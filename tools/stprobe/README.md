# stprobe — Phase 0C item 1: Flame ST-map convention

Measures the ST (UV) map convention **Flame's own downstream tools expect**, so
the White Water ST-map descriptor (`stMode`, `stOrigin`, and `StMap.{h,cpp}`)
can match it exactly. Per `docs/plan.md` and `docs/host-notes.md`, this is one of
the two blocking 0C questions.

This is **not** a plugin probe — it deliberately avoids round-tripping through our
own resampler, which could carry the same half-pixel error on both sides and still
close. It uses Flame's native ST consumers and a coordinate-encoded plate read
back as float EXR.

## Assets (`assets/`, generated by `make_st_assets.py`)

512×384 real pixels, non-square on purpose so any axis swap/flip is obvious.

- `WW_COORD.exr` — the **measuring stick**. Each pixel stores its own normalized
  position (R = normalized x, G = normalized y from bottom, B = 0.5). After Flame
  fetches from some source location, the output R,G **are** that location's
  coordinates: `x_fetched = R*512 - 0.5`, `yb_fetched = G*384 - 0.5`. Decode is
  exact and PAR-independent. This is the plate you feed as the **front / texture**.
- `ST_IDENTITY / ST_SHIFTX / ST_SHIFTY / ST_HALF / ST_OOR .exr` — the **UV maps**
  (U in R, V in G), authored with exactly-known values. See `manifest.json`.
- `WW_STSRC.exr` — optional human-readable landmark plate (red/green lines, corner
  blocks). Not needed for the numeric result; a visual gut-check only.

Regenerate: `python3 -m pip install OpenEXR && python3 make_st_assets.py`
(The airgapped Flame box needs none of this — carry the pre-generated EXRs over.)

## In Flame

Do this for **both** consumers — **Action** (UV-mapped surface) and the **native
ST Map node** (not the Matchbox one) — and at **both PAR 1 and PAR 2** (one
project; re-import the same files a second time at PAR 2).

Colour management is the one thing that will silently ruin this:

- Import the **UV maps tagged as UV Maps** (this is the production path and makes
  Flame treat them as coordinate data).
- Import **`WW_COORD.exr` as raw / data, no input transform** — it's the sampled
  texture and its values are the measuring stick; they must pass through
  untouched. Do **not** tag it as a UV Map.
- Export outputs **raw / linear, no view transform or LUT**, **float EXR**, full
  resolution, no proxy/resize. ZIP compression is fine (lossless).

For each `(node, par, map)`, apply the map to `WW_COORD` and render the node
output to:

```
out_<node>_<par>_<map>.exr
   node in {action, stmap}   par in {par1, par2}   map in {identity, shiftx, shifty, half, oor}
```

e.g. `out_action_par1_identity.exr`, `out_stmap_par2_shiftx.exr`.

- **PAR 1**: full battery (all 5 maps) for **both** nodes.
- **PAR 2**: at least `identity` + `shiftx` for both nodes (full battery welcome —
  it's what separates real-width vs canonical-extent normalization).

Drop the `out_*.exr` into `docs/measurements/<date>-stmap/` and record the Flame
build string, date, and the exact option labels you selected on each node.

## Analyze

```bash
python3 tools/stprobe/analyze_st_results.py docs/measurements/<date>-stmap/
```

Reports, per result and as a summary: denorm width (→ normalization basis),
half-pixel offset (→ `(i+0.5)/N` vs `i/N` vs `i/(N-1)`), origin (bottom-left vs
top-left/flipped), R/G channel layout (swap detector), and out-of-range behaviour
(clamp / wrap / black). That fixes the recorded convention and the descriptor
defaults.
